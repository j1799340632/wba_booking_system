# 第 7 轮：个人评估规划

继续只在本地 `feat/booking-assistant-local` 修改，未提交或推送 GitHub；未修改原 D 盘项目及原部署。

## 使用与交付

在学生菜单打开 **Assessment Plan**，或在 Book Slots 的助手中输入“帮我做评估规划”“我还差多少评估”。首次输入个人评估类型、目标次数、开始日期和截止日期。系统没有正式课程配额配置，因此不预填每类 10 次；原仪表盘写死的 10 次目标已移除，改为展示保存的个人目标。

每名学生保存一份当前计划，支持 1–20 个不同类型，每项 1–100 次，总数至多 1000，周期为 1–366 天（含截止日期）。可回顾已经结束的周期，也可设置未来周期。目标由学生依据课程或导师要求填写，不能将示例数当作官方要求。

计划包含：

- 各类型目标、已完成、已确认、待审批、仍需完成、还需发起的预约请求。
- 截止日期和状态：需要预约、待审批、已安排待完成、目标完成或已逾期。
- 按剩余日历周分配的新增请求数量，以及各周实际已有预约。
- 每种缺口至多 3 个真实可约候选；覆盖未来 30 天内且不超出计划截止日的场次。
- 既有记录缺少完成日期或场次时的提示；过期未完成预约的跟进提示。

候选依次通过真实时段查询与统一预约服务的可约检查，排除占用、学生或导师冲突、失效账号、禁用时段及伪造时间。用户选择 **Review session**，核对并勾选确认后，才创建 Pending 请求。目标保存、刷新、每周建议和模型回复都不会自动预约。

## 统计口径

| 数值 | 口径 |
| --- | --- |
| 已完成 | 当前学生、Completed 状态、`completed_time` 在计划周期内且不晚于当前业务时间 |
| 已确认 / 待审批 | 当前学生、实际预约场次尚未开始，完整位于计划周期内，分别为 Confirmed / Pending |
| 仍需完成 | `max(目标 − 已完成, 0)` |
| 还需请求 | `max(仍需完成 − 已确认 − 待审批, 0)`；待审批只是暂时覆盖，不算完成 |
| 总完成进度 | 各类型完成数分别封顶于其目标后求和；类型明细保留真实完成数 |
| 过期未完成 | 周期内已开始但仍 Pending / Confirmed 的场次，不抵扣缺口 |

取消、拒绝、逻辑删除的预约不计入完成或未来覆盖。场次模板被逻辑删除后，真实已完成记录仍参与统计。周期按 Australia/Sydney 本地日期计算，截止日包含整天；使用预约的实际 occurrence 时间，不用重复模板时间代替。

每周新增请求数按剩余周平均分配，余数优先分配到较早周，合计等于“还需请求”；已有预约按实际日期归周。它是可解释的数量节奏，不代表这些周一定有足够容量。不同目标的候选可能互相重叠，最终预约会再次检查冲突。

评估类型在目标保存时记录名称快照。原业务数据库通过名称连接时段类型；若字典类型改名或停用，旧目标保留历史含义、暂停推荐并提示重新核对，不静默替换为另一类型。

## 数据、权限与 AI 边界

新增 `student_assessment_plan` 表，主键为学生 ID，包含周期、目标 JSON、版本及创建/更新时间。JSON 由服务端根据有效字典构建。保存只操作当前登录学生，先锁学生行；不同版本的不同内容会被拒绝，避免两个标签页互相覆盖，相同内容的保存重试返回已保存版本。

`GET /student/assessmentPlan` 返回完整计划，`?summary=true` 返回不查询候选的进度摘要；`POST /student/assessmentPlan` 保存目标。学生身份和账号可用性均在服务端检查，管理员或导师继承学生路径权限也不能读取学生计划。

AI 新增 `PLAN_ASSESSMENTS` 意图，仅把用户引导到本人保存的规划并返回真实摘要。模型仍只接收用户文字、日期及公共字典，不接收成绩明细或整份目标记录，不编造课程配额，也不从对话直接修改目标。页面与确定性统计不依赖模型服务。

日期解析额外提供下一自然周各星期的明确日期，避免周一说“下周二”被误解成明天；搜索外部 Google Calendar 冲突约束仍需澄清，未加入该外部日历能力。

`scripts/local_demo.py start` 只在隔离演示库自动执行 `scripts/demo/migrate_assessment_plan.sql` 的增量建表。`mysql-init.sql` 也包含该表供全新初始化使用。本轮没有把迁移应用到原有部署。
